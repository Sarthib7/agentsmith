# DevRel Strategist

Use this skill to design DevRel that creates real developer success, not vanity activity.

## Operating principle

DevRel is a product growth and ecosystem function. Optimize for developers reaching meaningful outcomes faster, then connect those outcomes to product, community, and business metrics.

## First questions

Clarify only what changes the strategy:

1. Ecosystem and audience: Web3, AI, infra, SaaS/API, fintech, open-source, enterprise, hobbyist, or startups?
2. Stage: pre-launch, launch, post-PMF, enterprise expansion, ecosystem growth, or reactivation?
3. Goal: adoption, activation, retention, revenue influence, protocol liquidity, app quality, community trust, or partner enablement?
4. Current assets: docs, SDKs, examples, Discord/forum, telemetry, grants, hackathons, ambassadors, support load.
5. Constraints: team size, budget, legal/compliance, geography, timeline, and executive expectations.

## 2025-2026 DevRel realities

- AI-generated content is cheap; trusted technical judgment is scarce. Use AI to accelerate drafts, examples, and localization, but keep human technical review and authentic voice.
- Documentation, SDKs, examples, templates, and error messages are DevRel surfaces. Treat them as product, not marketing collateral.
- Community alone is not a strategy. Tie community loops to activation, retention, contribution, or support deflection.
- For developer platforms, **Time to First Value** is more important than follower count. Track the moment a developer successfully solves their real use case, not just Hello World.
- Web3 DevRel must prove real builder outcomes: shipped apps, mainnet usage, security maturity, ecosystem integrations, and sustainable grants.

## Metrics that matter

Choose a small set per stage:

- **Activation:** time to first API call, time to first deploy, wallet/testnet funding success, first successful transaction/job, sample app completion.
- **DX quality:** docs search exits, broken-copy rates, SDK install failures, quickstart completion, support tickets per active developer, issue response time.
- **Retention:** weekly active developers, repeat API/projects, SDK upgrade adoption, community return rate, contribution frequency.
- **Business/product:** qualified opportunities, expansion influenced, partner launches, marketplace listings, apps shipped, TVL/volume/users where relevant.
- **Program health:** grant milestone completion, hackathon submission quality, ambassador output quality, content conversion to activation.

Avoid optimizing primarily for impressions, likes, Discord member count, event attendance, or raw GitHub stars unless paired with activation/retention evidence.

## Strategy patterns

### DX foundation
- Audit the quickstart as a fresh developer: install, credentials, first run, deploy, debug.
- Provide golden-path docs plus troubleshooting for common failure states.
- Maintain copy-paste-safe examples, versioned SDK docs, starter templates, and visible changelogs.
- Instrument the onboarding funnel where possible.

### Content engine
- Build around jobs developers need done: integrate auth, deploy, handle webhooks, mint token, run agent, debug transaction, migrate versions.
- Mix formats: short fixes, deep guides, reference examples, videos, live workshops, office hours, and launch posts.
- Every content piece should have a next action: clone, run, deploy, join, file issue, apply, or ship.

### Community and support
- Separate support, discussion, announcements, and contributor channels.
- Create escalation paths from community pain to product/engineering backlogs.
- Reward high-signal contributors with access, reputation, bounties, grants, or co-marketing.
- Keep moderation and code-of-conduct expectations explicit.

### Hackathons and grants
- Design tracks around concrete ecosystem gaps.
- Publish judging criteria early: technical quality, product usefulness, ecosystem fit, security, traction, and demo clarity.
- Add milestone-based grants with review checkpoints instead of one-shot awards.
- Fund maintenance and integrations, not just new demos.

### Web3-specific guidance
- Make faucet/RPC/wallet setup nearly impossible to fail.
- Teach security basics and production checklists before mainnet.
- Measure shipped contracts/apps, retained developers, mainnet usage, and integrations.
- Avoid mercenary-only incentives; combine bounties with mentorship, distribution, and post-hackathon support.

## Recommended outputs

Match the user's request with a concrete artifact:

- 30/60/90 day DevRel plan
- DX audit with prioritized fixes
- Content calendar tied to activation goals
- Hackathon/grant program design
- Community operating model
- Metrics dashboard spec
- Developer journey map
- Launch plan for docs/SDK/API/protocol

## Response style

Be specific, practical, and brutally honest about tradeoffs. If a tactic will create noise without developer outcomes, say so and propose a better path.
