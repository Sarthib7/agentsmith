System overview

Observed source. The public examples declare three optional advisor roles. They do not establish whether any role is enabled or attached to a current session.

Chosen policy. Treat the “worker farm” as bounded logical work scopes, with the lead owning the final review. It is not a separately installed product.

Worker farms

Observed source. At the pinned Oh My Pi revision, task dispatch resolves policy and artifact leases. The ordinary route calls createAgentSession() in-process; an optional isolation route is a dispatch choice, not evidence of a separate operating-system process or a sandbox.

Chosen policy. Keep advisor review on the main session. The inspected code permits child opt-ins, so this is a policy boundary rather than a hard runtime restriction.

Configuration flow

Observed source. The model resolver considers request patterns, settings overrides, agent definitions, and inherited or default patterns. Repository examples describe role selectors and task overrides; resolution does not prove provider authorization or which backend handled a request.

Unknown runtime state. The active profile, usable provider access, and selected backend for any live request are not established here. A catalog entry also does not mean a skill is installed.

Harness experiment guidance

Chosen policy. The harness-experiment skill routes an explicitly requested experiment. Its package-local reference is the canonical procedure; the public workflow guide is a concise entry, and the skill source carries invocation instructions. The Workflows page shows the single summary flow.

Source evidence. The adaptation cites Harness2 at the immutable public revision 1cfe254e8d25b15f37048c3730134686abe60335, including its selection and budget sources. This attribution is not evidence that OMP integrates that implementation.

Runtime unknowns. A public source or catalog entry does not prove that the skill is installed, discoverable, or being used. Instructions alone do not enforce tool permissions, call/time/spend limits, or sandboxing; workspace separation is not an OS isolation guarantee.

No measured improvement is claimed. Whether the procedure changes real task quality, latency, or cost remains unknown.

Approval flow

Chosen policy. Trace a decision to its source revision, approve the scope directly, keep worker slices disjoint, and return integration and verification to the parent. A material scope or source change calls for fresh review.

Publication remains a separate decision from approving the work. This sequence is process guidance; the diagram is not a runtime lock or an approval interface.

Site build and publishing

Observed source. The parent build runs the Node workbench generator first, producing workbench.html and workbench-light.html. The Python builder validates the catalog and preflights six pages, shared assets, six architecture diagrams, and both generated views before writing _site/. The Pages workflow uploads that output and deploys it on pushes to main; it also supports a manual run.

Limit. This describes configured automation, not a current build or deployment. A generated artifact alone does not prove that a site was published.

Learnings

Three useful distinctions keep a diagram honest:

  • Scope is not isolation.

    A worker can have a bounded task and artifact lease without running in a separate process or a guaranteed sandbox.

  • Configuration is not capability.

    A selector or roster expresses intent. It does not prove provider entitlement, successful authorization, or a live invocation.

  • Validation is not publication.

    A generated catalog or _site/ is an output of a build, not evidence that the public deployment completed.
